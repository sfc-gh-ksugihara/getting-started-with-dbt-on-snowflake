1. dbt の基礎

1.1 dbt とは

dbt（data build tool）は、データウェアハウスに読み込み済みのデータを SQL で加工して、分析に使うテーブルやビューを作るためのツールです。データ処理の流れを ELT（Extract＝抽出、Load＝読み込み、Transform＝変換）で表すと、dbt が受け持つのは最後の T だけです。

このリポジトリでも役割が分かれています。S3 から Snowflake へのデータの読み込み（E と L）は setup/tasty_bytes_setup.sql の COPY INTO で行い、dbt はその後の変換（T）だけを担当します。

dbt で開発者が書くのは、基本的に SELECT 文だけです。CREATE VIEW や CREATE TABLE といった DDL、どのモデルから順に作るか、開発用と本番用のどちらに作るか、といった部分は dbt が受け持ちます。

① モデルを書くSELECT 文に、{{ ref() }} などの Jinja を混ぜて書く
→
② compileJinja を展開し、ref / source を実際のオブジェクト名に置き換えた SQL を作る
→
③ runCREATE VIEW … AS や CREATE TABLE … AS で包み、依存関係の順に Snowflake で実行する
→
④ 結果DEV や PROD スキーマにビューとテーブルができる

このほか、データの前提を確かめるテスト、YAML に書く説明文（ドキュメント）、Git でのレビューや CI/CD も、すべてテキストファイルで管理できます。SQL をファイルに分けてバージョン管理し、ソフトウェア開発と同じやり方でデータ変換を育てていく、というのが dbt の考え方です。

1.3 Jinja の書き方

dbt の .sql ファイルは、そのまま Snowflake に送られるわけではありません。Jinja（ジンジャ）というテンプレート言語で書かれた「SQL を作るためのひな形」で、dbt が実行の前に Jinja を展開して、ふつうの SQL にします。覚えておく記号は次の4つです。

書き方意味例
{{ … }}式。計算した結果が SQL の中に文字として埋め込まれる{{ ref('raw_pos_truck') }}
{% … %}文。if、for、set、マクロの定義など。それ自体は何も出力しない{% if custom_schema_name is none %}
{# … #}Jinja のコメント。コンパイル後の SQL には残らない—
{%-　-%}ハイフンを付けた側の空白と改行を取り除くgenerate_schema_name.sql で使用
ヒント

SQL の -- コメントは SQL にとってのコメントで、Jinja にとってはただの文字です。そのため -- {{ ref('x') }} のようにコメントの中に書いた Jinja も展開され、依存関係として扱われます。一時的に無効にしたいときは {# … #} で囲みます。

このページのコード例では、Jinja の部分をこの色で示します。

1.4 ref() と source()：依存関係と環境の切り替え

ref() と source() は dbt で最も大事な関数です。テーブル名を直接書く代わりにこれらを使うと、次の2つを dbt が自動で処理します。

  1. 依存関係（DAG）：orders.sql に {{ ref('raw_pos_truck') }} と書いてあるので、dbt は「raw_pos_truck を先に作り、そのあとで orders を作る」と判断します。並列に作れるモデルは同時に作り（並列数はプロファイルの threads）、+orders のような部分実行にもこの情報を使います。
  2. 環境の切り替え：同じコードが、dev ターゲットで実行すると DEV スキーマのオブジェクトを、prod ターゲットで実行すると PROD スキーマのオブジェクトを指します。

書いたコード（orders.sql の一部）と、dev ターゲットでコンパイルした結果

--target prod で実行すると、dev の部分が prod になります。データベース名はプロファイルの database、スキーマ名はプロファイルの schema（正確には後で説明するマクロ generate_schema_name の結果）から決まります。

ソースの参照（staging モデル）

使い分けの決まりはシンプルです。dbt が作っていないデータ（取り込み済みの元テーブル）は source()、dbt のモデルは ref() で参照し、テーブル名は直接書きません。ソースの場所は YAML に1回だけ書くので、場所が変わっても直すのは YAML の1か所だけで済みます。

1.5 マテリアライゼーション（モデルを何として作るか）

種類dbt が実行する内容向いている用途このリポジトリ
viewCREATE OR REPLACE VIEW … AS SELECT …。データを持たず、参照されるたびに計算する軽い加工、元データに近い層staging（8 本）
tableCREATE OR REPLACE TABLE … AS SELECT …。実行のたびに全件作り直す結合・集計が重いもの、よく参照されるものmarts（3 本）
incremental初回は全件作成し、2 回目以降は新しい行だけを追加またはマージする大きなテーブルで毎回の全件作り直しが重いとき未使用（7章の演習）
ephemeralオブジェクトを作らず、参照する側の SQL に CTE として埋め込まれる部品として使うだけの中間処理未使用

Snowflake 向けには、このほかに dynamic_table（ダイナミックテーブル）などもあります。このリポジトリでは使っていません。

マテリアライゼーションは、dbt_project.yml でフォルダ単位にまとめて指定するか、モデルのファイルの先頭に {{ config(materialized='table') }} と書いて個別に指定します。両方あるときは、より具体的なモデルファイル側の指定が優先されます。このリポジトリは dbt_project.yml でフォルダ単位に指定しています（4.2 節）。

補足：TRANSIENT テーブル

dbt の Snowflake アダプターは、テーブルを既定で TRANSIENT（一時的）テーブルとして作ります。TRANSIENT テーブルには Fail-safe 期間がないため、ストレージ費用が少し下がります。dbt はいつでも作り直せるので、多くの場合はこれで問題ありません。恒久テーブルにしたいときは transient: false を設定します。

1.6 テスト

dbt のテストは、前提に違反する行を返す SELECT 文です。dbt はその結果の件数を数え、0 件なら合格（PASS）、1 件以上なら不合格（FAIL）とします。たとえば not_null は「その列が NULL の行」を返す SELECT です。

種類書き方このリポジトリ
組み込みの汎用テストunique、not_null、accepted_values、relationships。YAML の列に名前を書くだけで使える__sources.yml で使用（not_null 34 個、unique 4 個、relationships 4 個）
自作の汎用テスト{% test 名前(model, column_name) %} … {% endtest %} で定義し、YAML から名前で呼ぶis_positive_amount（8 か所で使用、4.9 節）
単体テスト（singular test）tests/ フォルダに SELECT 文を 1 つ書いた .sql ファイルを置く。特定の業務ルールの確認に使うなし（7章の演習で追加）
パッケージのテストdbt_utils.accepted_range など。パッケージを入れると使えるコメントアウト中（4.11 節）

YAML でのキー名は data_tests: です。これは dbt 1.8 以降の名前で、古い資料では tests: と書かれています。テストが失敗しても止めずに警告だけにしたいときは、テストに severity: warn を設定します。

このリポジトリのテストは合計 50 個で、すべてソース（RAW スキーマのテーブル）に付いています。staging と marts のモデルにはテストがありません。「元データが前提どおりか」を確かめてから変換する、という構成です。

3. リポジトリの全体像

3.1 ディレクトリ構成

dbt にとって意味があるのは tasty_bytes_dbt_demo/ の中です。setup/、examples/、schedules.sql はふつうの SQL ファイルで、dbt のコマンドからは使われません（dbt_project.yml で指定したフォルダだけを dbt は読みます）。

3.2 データの流れ（DAG）

モデルの中の source() と ref() をたどると、次の図のようになります。左から右へデータが流れ、dbt もこの順に実行します。Workspace で compile を実行すると、DAG タブで同じ図を確認できます。

ソース（setup SQL が作るテーブル） staging モデル（ビュー） marts モデル（テーブル）

図から読み取れることが3つあります。

  • staging は「ソース 1 テーブルにつきビュー 1 本」の対応です。
  • raw_pos_order_header は 3 本のマートすべてから参照されています。このビューの元（RAW.ORDER_HEADER）に問題があると、影響はすべてのマートに及びます。
  • raw_pos_country は作られますが、どのマートからも使われていません。

3.3 実行後にできるオブジェクト

setup SQL を実行し、Workspace で dbt run（Profile は dev）を実行したあとのデータベース TASTY_BYTES_DBT_DB の中身です。Snowflake では、引用符で囲まない名前は大文字で保存されます。

4. コード解説

実行する順番に近い順で説明します。コードの左の数字はファイルの行番号です（抜粋のときは元のファイルの行番号）。

4.1 setup/tasty_bytes_setup.sql：環境とソースデータの準備

dbt を動かす前に、ウェアハウス、データベース、スキーマ、Git 連携、元データを用意するスクリプトです。dbt のファイルではなく、ふつうの SQL として実行します。中身は STEP 1〜6 に分かれています。

  • STEP 1（ウェアハウス）：データの読み込みが重いので XLARGE で作り、スクリプトの最後に SMALL へ下げます（ALTER WAREHOUSE tasty_bytes_dbt_wh SET WAREHOUSE_SIZE = SMALL;）。AUTO_SUSPEND = 60 は、使われなくなって 60 秒で自動停止する設定です。CREATE WAREHOUSE には IF NOT EXISTS が付いていないため、同じ名前のウェアハウスがあるとエラーになります。
  • STEP 2（データベースとスキーマ）：DEV と PROD は dbt が作るビュー・テーブルの置き場所、INTEGRATIONS は Git 連携用のシークレットの置き場所、RAW は元データの置き場所です。

dbt プロジェクトオブジェクトやタスクの実行ログ・トレースを残すための設定です。オブジェクトとタスクを置くスキーマに設定する必要があります。DEV と PROD に加えて、CI/CD のガイドでオブジェクトとタスクを置く PUBLIC スキーマにも設定しています。

  • API 統合は、Snowflake が GitHub にアクセスするための設定です。API_ALLOWED_PREFIXES は、自分のフォーク先の GitHub アカウントの URLに書き換えます。
  • シークレットは、非公開リポジトリのときに使う GitHub の認証情報（ユーザー名と Personal Access Token）です。公開リポジトリなら不要で、その場合は ALLOWED_AUTHENTICATION_SECRETS の行をコメントアウトします。なお、Workspace から公開リポジトリへ Push することはできません。

dbt deps で外部のパッケージを取得するときだけ必要です。packages.yml は全行コメントアウトされているので、そのままなら不要です。パッケージを試す場合（4.11 節）は、コメントを外して作成します。

  • 公開されている S3 バケットを外部ステージとして登録し、CSV を COPY INTO で RAW の 8 テーブルに読み込みます。ここまでが ELT の E と L です。
  • RAW のテーブルには、数値に見えるのに VARCHAR 型の列があります。たとえば country.city_population、order_header.order_tax_amount、order_header.order_discount_amount、customer_loyalty.children_count です。本来は staging で型をそろえる場面で、7章の演習の題材にしています。

4.6 marts/orders.sql：注文明細を横に結合したテーブル

  • 34〜46 行目：7 本の staging モデルを ref() で参照しています。これが 3.2 節の図の、orders に入る 7 本の矢印です。テーブル名を直接書いていないので、dev でも prod でも同じコードで動きます。
  • 1 行が表すもの（粒度）：FROM が注文明細（raw_pos_order_detail）なので、1 行＝注文の 1 明細です。注文ヘッダーの金額（30〜33 行目の order_amount〜order_total）は、同じ注文の明細の数だけ繰り返し入ります。このテーブルで SUM(order_total) を取ると、明細の数だけ重複して合計されるので注意してください。
  • 35〜44 行目は内部結合（JOIN）：トラック、メニュー、フランチャイズ、ロケーションのどれかに対応する行がない明細は、結果から落ちます。
  • 45〜46 行目は外部結合（LEFT JOIN）：ロイヤルティ会員でない顧客の注文も残し、顧客の列は NULL になります。
  • 14〜15 行目：フランチャイズのオーナー名に別名を付け、18〜19 行目の顧客の first_name / last_name と名前がぶつからないようにしています。
  • マテリアライゼーション：marts フォルダなのでテーブルになり、実行のたびに全件作り直されます。最も大きい注文明細を中心に 7 つを結合するため、このプロジェクトでは時間がかかりやすいモデルです。

注文単位で金額を合計したいときは、注文ごとに 1 行にしてから合計します。

4.8 marts/sales_metrics_by_location.py：Python モデル

dbt のモデルは Python でも書けます。Snowflake では Snowpark の DataFrame を使います。

  • 3 行目 def model(dbt, session)：Python モデルの決まった形です。dbt がこの関数を呼び出し、返した DataFrame（78 行目）をテーブルとして保存します。Python モデルはビューや ephemeral にはできず、テーブルか incremental になります。ここでは marts フォルダの設定でテーブルです。
  • 10〜12 行目 dbt.ref()：SQL モデルの {{ ref() }} にあたります。Python では Jinja が使えないので、この関数で参照します。戻り値は Snowpark の DataFrame で、依存関係も SQL モデルと同じように DAG に登録されます。
  • 15〜31 行目：トラックとロケーションを「トラックの拠点都市（PRIMARY_CITY）＝ロケーションの都市（CITY）」で結合し、ロケーションごとにトラックの台数を数えます。つまり TRUCK_COUNT は「そのロケーションがある都市を拠点にするトラックの台数」で、同じ都市のロケーションには同じ値が入ります。内部結合なので、トラックが 1 台もない都市のロケーションは結果に入りません。
  • 34〜43 行目：注文ヘッダーをロケーションごとに合計します。RAW の ORDER_TAX_AMOUNT は VARCHAR 型なので、41 行目の合計は数値への暗黙の型変換に頼っています。
  • 46〜61 行目：台数と売上を外部結合し、注文がないロケーションの売上を coalesce で 0 にします。
  • 64〜75 行目：<CITY> (Trucks: <TRUCK_COUNT>) という説明の列を追加します。
  • 列名が大文字の理由：Snowflake は、引用符で囲まない名前を大文字で保存します。Snowpark で列を指定するときは、その保存された名前（"LOCATION_ID"）に合わせます。
  • どこで動くか：Snowpark の DataFrame の操作は SQL に変換され、Snowflake のウェアハウスで実行されます。データを手元の Python に持ってくるわけではありません。dbt は Python モデルを Snowflake のストアドプロシージャとして実行します。
SQL と Python の使い分け

この程度の結合と集計は SQL でも書けます。このモデルは「Python でも書ける」ことを示すための例です。SQL では書きにくい処理や、Python のライブラリを使いたい処理に Python モデルを使い、それ以外は SQL にするのが一般的です。

4.9 tests/generic/test_is_positive_amount.sql：自作の汎用テスト

  • 1 行目：is_positive_amount という名前のテストを定義しています。YAML から呼ぶときの名前はこの {% test 名前 %} で決まり、ファイル名（test_is_positive_amount.sql）とは関係ありません。
  • 引数 model と column_name：YAML のどこにテストを書いたかによって、dbt が自動で渡します。__sources.yml で ORDER_HEADER の ORDER_TOTAL に付けた場合、model は tasty_bytes_dbt_db.RAW.ORDER_HEADER、column_name は ORDER_TOTAL になります。
  • 3〜5 行目：「0 以下の値を持つ行」を返します。これが 0 行なら合格です。NULL は対象外なので、NULL も許さないときは not_null と組み合わせます（ORDER_TOTAL はそうしています）。

テストが失敗したら、target/compiled/ の下にある、そのテストのコンパイル後の SQL を開いて実行すると、違反している行を確認できます。

4.10 macros/generate_schema_name.sql：スキーマ名の決め方

  • 役割：dbt は、モデルを作るスキーマを決めるときに必ず generate_schema_name マクロを呼びます。プロジェクトに同じ名前のマクロを置くと、dbt の組み込みのマクロの代わりにこちらが使われます。
  • 3 行目 target.schema：プロファイルで選んだターゲットの schema（dev または prod）です。
  • 4〜6 行目：custom_schema_name は、モデルに設定したカスタムスキーマ（+schema: … や config(schema=…)）です。このリポジトリではどのモデルにも設定していないので、常にこちらの分岐になり、ターゲットのスキーマ（DEV または PROD）に作られます。
  • 8〜10 行目：カスタムスキーマが設定されていれば、その名前をそのまま使います。| trim は前後の空白を除く Jinja のフィルターです。
  • {%- と -%}：マクロの戻り値は「出力された文字」なので、改行や空白が混ざるとスキーマ名がおかしくなります。ハイフンで空白を取り除いています。

このマクロの効果が出るのは、カスタムスキーマを設定したときです。たとえば dbt_project.yml の staging に +schema: staging を足すと、次のように変わります。

マクロ--target dev--target prod
dbt の組み込み（<ターゲットのスキーマ>_<カスタムスキーマ>）dev_stagingprod_staging
このリポジトリのマクロstagingstaging
注意

このマクロのままカスタムスキーマを使うと、dev で実行しても prod で実行しても同じ STAGING スキーマに作られ、開発中の実行で本番のオブジェクトを上書きしてしまいます。環境ごとに分けたい場合は、Snowflake ドキュメントの例のように、10 行目を {{ custom_schema_name | trim }}_{{ target.name | lower }} にして staging_dev と staging_prod に分けるなどの方法があります。

4.11 packages.yml：外部パッケージ

  • 全行がコメントアウトされているので、いまは外部パッケージを使っていません。dbt deps を実行しても何も取得しません。
  • dbt_utils は、よく使うマクロやテストを集めたパッケージです。__sources.yml でコメントアウトされている dbt_utils.accepted_range（値の範囲）や dbt_utils.expression_is_true（任意の条件式）はこのパッケージのテストです。
  • dbt_semantic_view は、Snowflake のセマンティックビューを dbt のモデルとして作るためのパッケージです。

パッケージを使う手順は次のとおりです。

  1. setup SQL の STEP 5 のコメントを外して、ネットワークルールと外部アクセス統合（dbt_ext_access）を作る。
  2. packages.yml のコメントを外す。
  3. Workspace で Deps を選び、実行ボタン横の下向き矢印から外部アクセス統合に dbt_ext_access を指定して実行する。
  4. package-lock.yml ができ、パッケージは dbt_packages/ に入る（dbt_packages/ は .gitignore で Git の対象外）。
注意

packages.yml にパッケージを書いたのに dbt deps を実行していないと、ほかの dbt コマンドは失敗します。なお、外部アクセス統合を指定してデプロイすると、デプロイ時に dbt deps が自動で実行されます。

4.12 schedules.sql：タスクで定期実行する

2 つのタスクを親子につないだ、小さなタスクグラフです。

  • 3〜4 行目：変更する前に、両方のタスクをいったん停止します。IF EXISTS なので、初回（タスクがまだない）でもエラーになりません。
  • 7〜11 行目（親タスク）：12 時間ごとに、プロジェクトの一部を build します。業務で早めに必要なモデルだけを先に作る、という想定の例です。dbt プロジェクトを実行するタスクには、ウェアハウスの指定が必要です。
  • 14〜18 行目（子タスク）：AFTER で親タスクの後に実行し、プロジェクト全体を build します。親タスクが失敗すると（たとえば build の中のテストが失敗すると）、子タスクは実行されません。
  • 22〜23 行目：作ったタスクは停止した状態なので、再開（RESUME）します。子から親の順に再開します。
  • execute dbt project … args='…'：args には、dbt コマンドの dbt より後ろの部分をそのまま書きます。
このファイルをそのまま使う前に
  • 11 行目の --select raw_customers stg_customers customers：このプロジェクトには、この名前のモデルはありません。dbt は警告を出すだけで、何もビルドしません。たとえば --select +customer_loyalty_metrics のように、実在するモデルに書き換えます。
  • 実行するオブジェクトの名前：tasty_bytes_dbt_object_gh_action は、CD ワークフロー（pr_merged.yml）が作るオブジェクトです。5章の手順で Workspace からデプロイした場合は、オブジェクト名が TASTY_BYTES_DBT_PROJECT なので書き換えます。
  • 作られる場所：タスク名とオブジェクト名をデータベース名・スキーマ名で修飾していないので、実行したときの現在のデータベースとスキーマが使われます。

Workspace の画面からタスクを作ることもできます（5章の手順 12）。画面から作ると、次のような SQL のタスクができます（Snowflake ドキュメントの例）。

4.13 CI/CD：ci_cd_setup.sql と GitHub Actions（任意）

GitHub への Pull Request と main へのマージをきっかけに、自動でテストとデプロイを行う仕組みです。基本のハンズオンでは使いませんが、運用のイメージをつかむために読んでおくと役に立ちます。

ci_cd_setup.sql：GitHub Actions 用のサービスユーザー

  • 43 行目 TYPE = SERVICE：人ではなくプログラムが使うユーザーです。
  • 44〜48 行目：OIDC（OpenID Connect）による認証です。パスワードや長期間有効なトークンを GitHub に保存する代わりに、GitHub Actions が実行のたびに発行する短期間のトークンで Snowflake にログインします。SUBJECT は「どのリポジトリの、どの environment からのログインを許すか」で、your_repo_org/your_dbt_repo を自分のフォークに書き換えます。

  • 16 行目 environment: prod：サービスユーザーの SUBJECT の末尾（environment:prod）と一致させる必要があります。
  • 19〜22 行目：接続先のアカウントは GitHub の Secrets から、データベースとスキーマは Variables から読みます。このデータベースとスキーマは dbt プロジェクトオブジェクトを置く場所です。モデルが作られる場所は、プロファイルの schema（dev または prod）で決まります。
  • 39 行目 -x：設定ファイルを使わず、環境変数から一時的な接続を作るオプションです。
  • 44 行目 snow dbt deploy：--source の dbt プロジェクトのフォルダを、テスト用の dbt プロジェクトオブジェクトとしてデプロイします。--dbt-version は実行に使う dbt のバージョンです。
  • 51 行目 snow dbt execute … build --target dev：デプロイしたオブジェクトで、DEV スキーマに対して build（モデルの作成とテスト）を行います。失敗すると Pull Request のチェックも失敗します。

5. ハンズオンの手順

Snowflake の Getting started チュートリアルと同じ流れです。名前（ウェアハウス、データベース、オブジェクト）はチュートリアルに合わせています。

始める前に
  • GitHub のアカウントと、Snowflake で ACCOUNTADMIN ロールを使えるユーザーが必要です（このリポジトリは ACCOUNTADMIN を前提にしています）。
  • GitHub では、公開リポジトリのフォークは公開リポジトリになります。Workspace から公開リポジトリへは Push できないので、手順 10 の Push まで試す場合は、フォークの代わりに非公開のコピーを作り、Personal Access Token を用意してください。

  1. リポジトリをフォークする

    Snowflake-Labs/getting-started-with-dbt-on-snowflake を開き、Fork の横の下向き矢印から Create a new fork を選びます。

  2. Workspace を作る前に必要なものを作る（SQL）

    Snowsight で SQL を実行できる画面（ワークシートなど）を開き、次の SQL を実行します。<…> の部分は自分の値に書き換えます。内容は tasty_bytes_setup.sql の STEP 1、2、4 と同じです。

    パッケージ（4.11 節）も試す場合は、STEP 5 のネットワークルールと外部アクセス統合もここで作ります。

  3. Git リポジトリにつないだ Workspace を作る

    1. Snowsight のナビゲーションメニューで Projects → Workspaces を選ぶ。
    2. Workspace の一覧の Create Workspace で From Git repository を選ぶ。
    3. Repository URL にフォークの URL（例：https://github.com/<アカウント>/getting-started-with-dbt-on-snowflake.git）を入力する。
    4. Workspace name に tasty_bytes_dbt を入力し、API integration で TB_DBT_GIT_API_INTEGRATION を選ぶ。
    5. 公開リポジトリなら Public repository を、非公開なら Personal access token を選んで、手順 2 のシークレット（TASTY_BYTES_DBT_DB.INTEGRATIONS.TB_DBT_GIT_SECRET）を指定し、Create を選ぶ。

    確認：Workspace に tasty_bytes_dbt_demo フォルダが表示される。

  4. ソースデータを作る

    1. Workspace で tasty_bytes_dbt_demo/setup/tasty_bytes_setup.sql を開く。
    2. 手順 2 で実行済みの文をコメントアウトする：CREATE WAREHOUSE、CREATE OR REPLACE SECRET、CREATE OR REPLACE API INTEGRATION（STEP 5 を作った場合はそれも）。
    3. エディタ右上のコンテキストの選択で、ウェアハウス TASTY_BYTES_DBT_WH を選ぶ。
    4. すべてを実行する（Mac は Cmd+Shift+Enter）。

    確認：Output タブに tasty_bytes_dbt_db setup is now complete と表示される。スクリプトの最後でウェアハウスは SMALL に戻る。

  5. プロファイルを確認する

    tasty_bytes_dbt_demo/dbt_projects_profiles.yml を開き、データベースとウェアハウスの名前が自分の環境と合っているか確かめます（4.3 節）。名前を変えていなければ、そのままで動きます。

    確認：エディタ上部の Profile の一覧に dev と prod が表示される。

  6. （任意）Deps を実行する

    packages.yml がコメントアウトのままなら省略できます。パッケージを試す場合は、4.11 節の手順で実行します。

  7. Compile して DAG とコンパイル後の SQL を見る

    1. Project に tasty_bytes_dbt_demo、Profile に dev、コマンドに Compile を選んで実行する。
    2. エディタ下の DAG タブを開く。ドラッグで移動、＋と－で拡大・縮小できる。
    3. DAG の orders のタイルを選んでファイルを開き、右上の View Compiled SQL を選ぶ。

    確認：DAG が 3.2 節の図と同じ形になっている。コンパイル後の SQL では {{ ref(…) }} が tasty_bytes_dbt_db.dev.… に置き換わっている。

  8. Run して、できたオブジェクトを確かめる

    1. Profile を dev にして、コマンド Run を実行する。Output は実行が終わってから表示される。
    2. examples フォルダの横の ＋ から SQL File を選び、dbt_sandbox.sql を作る。
    3. 次の SQL を実行する。

    確認：DEV スキーマにテーブル CUSTOMER_LOYALTY_METRICS、ORDERS、SALES_METRICS_BY_LOCATION と、8 本のビューがある（3.3 節）。

  9. Test と Build を実行する

    1. コマンド Test を実行する。ソースに付いた 50 個のテストが実行される。
    2. コマンド Build を実行する。モデルの作成とテストが DAG の順に行われる。

    確認：Output で各テストの PASS / FAIL を確かめる。FAIL のテストがあれば、4.9 節の方法で違反している行を確認する。Build では、FAIL になったテストの下流のモデルがスキップされる。

  10. （非公開リポジトリのみ）変更を Push する

    Changes を選ぶと、変更したファイルだけが表示されます（A＝追加、M＝変更、D＝削除）。ブランチが main であることを確かめて Push を選び、コミットメッセージを入力して Push します。

  11. dbt プロジェクトオブジェクトとしてデプロイする

    1. エディタ右側の Connect → Deploy dbt project を選ぶ。
    2. Select database and schema で TASTY_BYTES_DBT_DB と DEV を選ぶ。
    3. Create dbt Object を選び、名前に TASTY_BYTES_DBT_PROJECT を入力して Deploy を選ぶ。

    確認：SHOW DBT PROJECTS LIKE 'tasty%'; でオブジェクトが表示される。Connect のメニューの View project で詳細ページ（DAG、実行履歴）を開ける。

    デプロイ後に Workspace でファイルを変えても、オブジェクトは自動では変わりません。反映するときは Connect → Redeploy dbt project を選びます。

  12. タスクで定期実行する

    1. dbt プロジェクトのメニューの横のカレンダーのアイコンを選び、+ Create new を選ぶ。
    2. Schedule name に run_prepped_data_dbt、Frequency に Custom を選んで cron 式 1 */12 * * * を入力する（12 時間ごと、毎時 1 分）。
    3. dbt properties で、Operation に run、Profile に dev、Additional flags に --select customer_loyalty_metrics を入力して Create を選ぶ。

    確認：カレンダーのアイコン → スケジュールの … → View で、タスクの定義（4.12 節の最後の SQL と同じ形）が表示される。すぐに 1 回動かしたいときは EXECUTE TASK tasty_bytes_dbt_db.dev.run_prepped_data_dbt; を実行し、プロジェクトの詳細ページで実行履歴を確かめる。

  13. 後片付け

    タスクを残すと 12 時間ごとにウェアハウスが動きます。続けて使わない場合は、少なくともタスクを停止してください。共有のアカウントでは、削除してよいものか確かめてから実行します。

    Workspace は、Workspace のメニューの横の縦三点のメニューから Delete で削除します。

6. つまずきやすい点

起きること原因対処
Workspace を作るときに Git リポジトリにつながらないAPI 統合の API_ALLOWED_PREFIXES がフォーク先と違う。非公開リポジトリなのにシークレットを指定していない、または Personal Access Token の権限が足りないAPI_ALLOWED_PREFIXES を https://github.com/<自分のアカウント> にする。シークレットとトークンを確かめる
setup SQL を Workspace で実行すると「already exists」のエラーになるCREATE WAREHOUSE に IF NOT EXISTS がなく、手順 2 で作ったウェアハウスと重なる実行済みの文をコメントアウトしてから実行する
setup SQL を実行したあと、Pull や Push が認証エラーになるファイルの CREATE OR REPLACE SECRET がダミーの値（YOUR_PERSONAL_ACCESS_TOKEN）のまま実行され、本物のシークレットを上書きしたシークレットを正しい値で作り直す。Workspace 内で setup SQL を実行するときは、シークレットの文もコメントアウトする
dbt deps がパッケージを取得できない外部アクセス統合がない、または実行時に指定していないsetup SQL の STEP 5 を作り、Deps の実行時に dbt_ext_access を指定する
packages.yml のコメントを外したら、ほかのコマンドが失敗するdbt deps を実行していない先に Deps を実行する
Workspace から Push できない公開リポジトリ（公開リポジトリのフォークを含む）には Push できないPush を試すなら非公開のコピーを使う
実行中に Output に何も表示されないWorkspace は実行が終わってからまとめて表示する。orders は大きな表を結合するので時間がかかる終わるまで待つ
examples/tasty_bytes_example_query.sql がエラーになるこのセットアップでは作られない tb_101 データベースを参照しているtasty_bytes_dbt_db.raw に書き換える（4.14 節）
schedules.sql の親タスクが何も作らない--select のモデル名（raw_customers など）がこのプロジェクトにない実在するモデル名にする（4.12 節）
GitHub Actions の deploy が失敗する--source ./tasty_bytes のフォルダが存在しない（実際は tasty_bytes_dbt_demo）--source ./tasty_bytes_dbt_demo にする（4.13 節）
ci_cd_setup.sql が構文エラーになる99 行目の <other required rules> が書き換え用の目印のまま目印を消すか、必要なネットワークルールに置き換える
カスタムスキーマを設定したら、dev と prod が同じスキーマに作られたgenerate_schema_name マクロがカスタムスキーマ名をそのまま使うマクロでターゲット名を付ける（4.10 節）
orders で売上を合計すると大きすぎるorders は 1 行＝1 明細で、注文の金額が明細の数だけ重複している注文ごとに 1 行にしてから合計する（4.6 節）

7. 追加の演習

時間が余ったら試してください。すべて dev ターゲットで実行します。ここのコードはこの資料のために書いたもので、実データでの実行結果は確認していません。テストが FAIL になった場合も、なぜそうなったかを調べることが練習になります。

7.1 既存のモデルに列を足す

customer_loyalty_metrics.sql の 9 行目の前に、注文件数の列を 1 行足します。

ファイルを開いたまま再生ボタン（Cmd+Enter）を押すと、このモデルだけが作り直されます（dbt run --select customer_loyalty_metrics）。

7.2 新しいモデルとテストを足す

日ごとの注文件数と売上のモデルを作り、YAML でテストを付けます。

コマンド Build の引数に --select daily_sales を指定して実行すると、モデルの作成とテストがまとめて行われます。marts フォルダに置いたので、自動でテーブルになります。DAG にも新しいノードが現れます。

7.3 単体テスト（singular test）を書く

「日ごとの売上の合計」と「注文ヘッダーの売上の合計」が一致するかを確かめるテストです。一致しないときだけ 1 行を返します。

--select daily_sales で Test を実行すると、このテストも対象になります（daily_sales を参照しているため）。

7.4 staging で型をそろえる

RAW の order_tax_amount と order_discount_amount は VARCHAR 型です。staging で数値に変換すると、下流のモデルは型を気にせずに使えます。

TRY_TO_NUMBER は、数値に変換できない値を NULL にします。変更の影響は下流のすべてのマートに及ぶので、--select raw_pos_order_header+ で Build して確かめます。

7.5 incremental モデルを作る

2 回目以降は新しい行だけを処理するモデルです。

  • 1 行目：ファイルの先頭の config() は、dbt_project.yml のフォルダ単位の設定（table）より優先されます。
  • 5〜7 行目：is_incremental() は、テーブルがすでにあり、--full-refresh を付けていないときだけ真になります。初回は全件、2 回目以降は「すでにある最新の日時より新しい行」だけを処理します。{{ this }} はこのモデル自身のテーブルです。
  • このハンズオンのデータは増えないので、2 回目の実行で追加される行は 0 件です。Output やクエリ履歴で、1 回目と 2 回目に実行された SQL の違いを見てください。全件作り直すときは --full-refresh を付けます。
  • 注文ヘッダーを全件コピーするので、実行に時間がかかり、ストレージも使います。試したあとは削除してかまいません。

7.6 schedules.sql を直して使う

4.12 節の注意に沿って、11 行目の --select を +customer_loyalty_metrics に、オブジェクト名を手順 11 で作った TASTY_BYTES_DBT_PROJECT に変え、USE SCHEMA tasty_bytes_dbt_db.dev; を実行してからファイルを実行します。--target prod なので、PROD スキーマにオブジェクトが作られます。試したあとは、両方のタスクを停止（ALTER TASK … SUSPEND）してください。

7.7 dbt_utils のテストを試す

4.11 節の手順で dbt_utils を入れ、__sources.yml の 15〜17 行目（COUNTRY_ID の accepted_range）のコメントを外します。--select source:tb_101.COUNTRY で Test を実行すると、COUNTRY に付いたテストだけが実行されます。
